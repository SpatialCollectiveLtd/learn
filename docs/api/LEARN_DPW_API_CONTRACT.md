## 1. Context & Purpose

The Learn Platform is undergoing an architectural reset. Previously, Learn maintained its own user database, attendance records, work tracking, and authentication. Going forward:

- **DPW App** is the single source of truth for: user identity, roles, authentication, attendance, work performance, and payments.
- **Learn Platform** is responsible for: LMS (training content & progress), Notification Centre (in-platform comms), and dashboards that render data from DPW.

This document defines every API endpoint the Learn Platform needs from the DPW App. The DPW team implements these endpoints; the Learn team consumes them.

### What Changes

| Concern | Before (Learn owned) | After (DPW owns) |
|---|---|---|
| User identity | `youth_participants`, `staff_members` tables | DPW user database |
| Authentication | Learn issued JWTs from local DB lookup | DPW validates credentials, Learn issues session JWTs |
| Attendance | `attendance_records` table in Learn DB | DPW attendance system |
| Work tracking | `youth_work_days`, `youth_osm_stats` | DPW performance data |
| Payments | Proxied from DPW | DPW (unchanged) |
| Training progress | `youth_training_progress` in Learn DB | **Still Learn** — no change |
| Notifications | New feature | **Still Learn** — no change |

### What the DPW App Can Retire

Once Learn is consuming DPW APIs directly, the following Learn endpoints can be decommissioned:

- `GET /api/external/dpw-sync` — DPW previously pulled data from Learn. This endpoint will be removed.
- `GET /api/external/osm-mappings` — OSM username sync. Will be removed (QGIS replaces OSM workflow).

## 2. Server-to-Server Authentication

All Learn → DPW API calls use a shared secret in the `Authorization` header:

```
Authorization: Bearer <LEARN_DPW_SHARED_SECRET>
```

- The secret is generated by the DPW team and shared securely with Learn.
- Learn stores it as `DPW_API_SECRET` in its environment variables.
- DPW validates this header on every request from Learn.
- This secret is **never** sent to the browser — only used in Learn's server-side API routes.

### Rate Limiting

Learn expects to make:
- **Auth calls:** ~200/day (youth logins) + ~20/day (admin launches)
- **User data calls:** ~500/day (profile lookups, list queries)
- **Performance/attendance calls:** ~300/day (dashboard views)
- **Reference data calls:** ~50/day (settlements, modules — cached on Learn side for 60s)

**Suggested DPW rate limit:** 100 requests/minute from Learn's server IP. Learn will respect `429 Too Many Requests` and implement exponential backoff.

## 3. Error Response Format

All DPW endpoints should return errors in this consistent format:

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "No user found with ID KAY999"
  }
}
```

### Standard Error Codes

| HTTP Status | Code | Meaning |
|---|---|---|
| 400 | `INVALID_REQUEST` | Missing or malformed parameters |
| 401 | `UNAUTHORIZED` | Invalid or missing `Authorization` header |
| 403 | `FORBIDDEN` | Valid auth but insufficient permissions |
| 404 | `USER_NOT_FOUND` | Requested user does not exist |
| 404 | `RESOURCE_NOT_FOUND` | Requested resource does not exist |
| 429 | `RATE_LIMITED` | Too many requests |
| 500 | `INTERNAL_ERROR` | DPW server error |

## 4. Authentication Endpoints

### 4.1 Youth Login

Youth enter their ID on Learn's login page. Learn forwards the ID to DPW for validation.

```
POST /api/learn/auth/youth
```

**Request:**
```json
{
  "youth_id": "KAY1799DM"
}
```

**Success Response (200):**
```json
{
  "success": true,
  "data": {
    "user_id": "KAY1799DM",
    "full_name": "David Mandu",
    "email": "david.mandu@example.com",
    "phone_number": "+254712345678",
    "role": "youth",
    "settlement": "Kayole",
    "module": "digitization",
    "module_assignment": "mapper",
    "trainer_name": "Jane Mwangi",
    "cohort": "2026-A",
    "is_active": true,
    "enrolled_at": "2025-12-01T00:00:00.000Z"
  }
}
```

**Error (401) — Invalid ID:**
```json
{
  "success": false,
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Youth ID not recognized"
  }
}
```

**Error (403) — Inactive:**
```json
{
  "success": false,
  "error": {
    "code": "ACCOUNT_INACTIVE",
    "message": "This account has been deactivated"
  }
}
```

**Learn's behaviour:** On success, Learn signs its own JWT with the returned profile data and stores it in the browser. Learn does **not** store the user in its own database.

### 4.2 Admin/Trainer Launch Token Verification

Admins and trainers are already authenticated in DPW App via Google. When they click "Launch Learn" in DPW, the DPW App generates a signed one-time token and redirects:

```
https://learn.spatialcollective.co.ke/auth/launch?token=<one-time-token>
```

Learn's server-side route then verifies this token with DPW:

```
POST /api/learn/auth/verify-launch-token
```

**Request:**
```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

**Success Response (200):**
```json
{
  "success": true,
  "data": {
    "user_id": "STEA8103SA",
    "full_name": "James Admin",
    "email": "james@spatialcollective.com",
    "role": "admin",
    "settlement": null,
    "permissions": ["view_all_youth", "manage_notifications", "view_reports"],
    "is_active": true
  }
}
```

**Error (401) — Invalid token:**
```json
{
  "success": false,
  "error": {
    "code": "INVALID_TOKEN",
    "message": "Token is invalid, expired, or already used"
  }
}
```

### Token Requirements (DPW implements)

| Property | Requirement |
|---|---|
| Format | Signed JWT or HMAC-signed opaque token |
| Expiry | ≤ 60 seconds from generation |
| Single use | Token is marked as used after first verification call |
| Payload | Must encode: `user_id`, `role`, `issued_at` |
| Signing key | Shared secret between DPW and Learn (`DPW_LAUNCH_TOKEN_SECRET`) — or DPW signs with its own key and verifies server-side |

### DPW App Requirements

The DPW App must:
1. Add a **"Launch Learn"** button (visible to admins + trainers)
2. On click: generate a signed one-time token encoding the current user
3. Redirect the browser to `https://learn.spatialcollective.co.ke/auth/launch?token=<token>`
4. Implement `POST /api/learn/auth/verify-launch-token` to validate the token and return the user profile

## 7. What Learn Provides Back to DPW (Optional Webhooks)

Learn owns training progress data. If DPW needs training completion status, Learn can provide it in two ways:

### Option A: DPW queries Learn (recommended for simplicity)

```
GET https://learn.spatialcollective.co.ke/api/dpw/training-status/{user_id}
```

**Response:**
```json
{
  "success": true,
  "data": {
    "user_id": "KAY1799DM",
    "training_complete": true,
    "modules": [
      {
        "module_type": "mapper",
        "steps_completed": 7,
        "steps_total": 7,
        "completed_at": "2025-12-15T10:00:00.000Z"
      }
    ]
  }
}
```

### Option B: Learn sends webhook on completion

```
POST https://app.spatialcollective.com/api/webhooks/learn/training-complete
Authorization: Bearer <LEARN_DPW_SHARED_SECRET>

{
  "event": "training_complete",
  "user_id": "KAY1799DM",
  "module_type": "mapper",
  "completed_at": "2025-12-15T10:00:00.000Z",
  "steps_completed": 7
}
```

**DPW team: please confirm which option you prefer.**

## 8. TypeScript Interfaces

These are the exact types Learn will use. DPW response shapes must match these.

```typescript
// === Auth ===

interface YouthAuthRequest {
  youth_id: string;
}

interface LaunchTokenRequest {
  token: string;
}

interface UserProfile {
  user_id: string;
  full_name: string;
  email: string | null;
  phone_number: string | null;
  role: 'youth' | 'trainer' | 'admin' | 'superadmin';
  settlement: string | null;
  module: string | null;
  module_assignment: string | null;
  trainer_id: string | null;
  trainer_name: string | null;
  cohort: string | null;
  is_active: boolean;
  enrolled_at: string | null;
  contract: {
    has_signed: boolean;
    signed_at: string | null;
    start_date: string | null;
    end_date: string | null;
    total_contracted_days: number | null;
  } | null;
}

interface AdminProfile {
  user_id: string;
  full_name: string;
  email: string;
  role: 'trainer' | 'admin' | 'superadmin';
  settlement: string | null;
  permissions: string[];
  is_active: boolean;
}

// === User List ===

interface UserListItem {
  user_id: string;
  full_name: string;
  role: string;
  settlement: string | null;
  module: string | null;
  module_assignment: string | null;
  is_active: boolean;
}

interface UserListResponse {
  users: UserListItem[];
  pagination: {
    page: number;
    per_page: number;
    total: number;
    total_pages: number;
  };
}

// === Attendance ===

interface AttendanceRecord {
  date: string;          // YYYY-MM-DD
  status: 'present' | 'absent' | 'excused';
  submitted_by: string;
  submitted_at: string;  // ISO 8601
  notes: string | null;
}

interface AttendanceResponse {
  user_id: string;
  total_days_attended: number;
  date_range: {
    from: string;
    to: string;
  };
  records: AttendanceRecord[];
}

// === Performance ===

interface PerformanceSummary {
  total_days_worked: number;
  total_output: number;
  output_unit: string;
  daily_target: number;
  average_daily_output: number;
  best_day_output: number;
  target_met_days: number;
  attendance_rate: number;  // 0-1
}

interface ContractProgress {
  contracted_days: number;
  days_worked: number;
  days_remaining: number;    // Floors at 0
  percent_complete: number;  // 0-100
}

interface WorkHistoryEntry {
  date: string;          // YYYY-MM-DD
  output: number;
  target: number;
  target_met: boolean;
  status: 'pending' | 'approved' | 'rejected';
}

interface PerformanceResponse {
  user_id: string;
  module: string;
  summary: PerformanceSummary;
  contract_progress: ContractProgress;
  work_history: WorkHistoryEntry[];
}

// === Payments ===

interface PaymentCycle {
  cycle_id: string;
  cycle_name: string;
  period: {
    from: string;  // YYYY-MM-DD
    to: string;
  };
  days_worked: number;
  earnings: number;
  quality_score: number | null;
  status: 'paid' | 'pending' | 'processing';
  paid_at: string | null;
}

interface PaymentsResponse {
  user_id: string;
  module: string;
  payment_rate_kes: number;
  total_earnings: number;
  total_paid: number;
  total_pending: number;
  cycles: PaymentCycle[];
}

// === Reference Data ===

interface Settlement {
  settlement_id: string;
  name: string;
  full_name: string;
  region: string;
  is_active: boolean;
}

interface Module {
  module_id: string;
  name: string;
  description: string;
  daily_target: number;
  payment_rate_kes: number;
  output_unit: string;
  is_active: boolean;
  settlements: string[];
}

interface Trainer {
  trainer_id: string;
  full_name: string;
  email: string;
  settlement: string;
  module: string;
  youth_count: number;
  is_active: boolean;
}

// === Standard Envelope ===

interface ApiSuccess<T> {
  success: true;
  data: T;
}

interface ApiError {
  success: false;
  error: {
    code: string;
    message: string;
  };
}

type ApiResponse<T> = ApiSuccess<T> | ApiError;
```
